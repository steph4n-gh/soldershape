## Done predicate

The README, local guides, current screenshots, captioned still-capture video and static launch page must describe the same real-board decision. The public-facing example must distinguish the 300 and 330 micrometer assumptions, numerical fixture outcomes and absent physical qualification. Every displayed force must come from retained native evidence. Links, recorded selectors, media and actual downloads must work in the running preview. The exact committed source must build an extractable release candidate and pass its applicable checks. Public-release gaps must remain explicit. No new public audience or repository is created during this preparation phase.

## Throughput checkpoint

The parallel coverage slice has four steps. Frame, fan out, aggregate, and report. Its three workers cover documentation, asset preparation tools, and public-release audit. Each has separate writable paths and uses the configured inherited parent model. Root merges and verifies their results.

- Blocking first steps. Inspect the current Site identity and audience, source helper, maintained media and launch scripts before edits. Preserve old numerical receipts and source archives.
- Independent workstreams. One documentation owner edits prose. One asset-tool owner edits the existing preparation and check scripts. One read-only release auditor inspects history, notices and packaging. Root owns Site source, captures, generated assets, preview and final packaging.
- Shared mutable state. Writers have disjoint paths. The asset owner does not run generators. Root is the only writer of screenshots, generated Site media, inventory, source mirror and release receipts. Sites credentials stay in session memory and hidden stdin.
- Smallest safe decomposition. Reuse the existing static page, recorded evidence, media generator and release builder. No hosted solver, upload service, frontend dependency or new numerical model is needed.

## Sequence and acceptance

1. Capture six actual application views on the current walkthrough and name their exact input conditions.
2. Update the existing docs and recorded launch selector around the same question and two gaps.
3. Package both immutable native archives with original notices. Build a 36-second video from six stills, six seconds each. Label editorial timing, no audio and no solver-speed claim.
4. Check static references, source identities, both recorded outcomes, captions, video metadata and actual browser downloads. Check desktop and narrow layout.
5. Run current application checks and independent public-release source review. Preserve negative results and qualification limits.
6. Commit the source, build a new complete candidate from that exact commit, extract it without Git or an engine cache, and verify its manifest and newcomer workflow.
7. Save the reviewed Site version against its existing project identity without changing its audience. Report the remaining source-publication, security-channel and public-access steps.

## Chosen representation

The static recorded comparison uses a small `soldershape.launch-walkthrough.v1` JSON document generated from the two existing Board archives. Each scenario has an ID, label, held gap, source archive identity, evidence URL, server screen and original review rows. Site code selects a scenario and a row. It does not compute forces or invent physical qualification. The original app owns live computation.

Architectural bakeoff is unnecessary for this mechanical extension of the existing recorded selector. The prior walkthrough design is settled. The bespoke pre-release sequence provides the verification gates.
